# Пошаговая инструкция: прокси для Liv в один сервис (direct-mode)

Этот документ описывает **упрощённый вариант** прокси: один Cloudflare Worker
без Fly.io, без карт, без vmware-чик и без серверов. Он короче и быстрее, чем
вариант с цепочкой, но менее надёжный — почему именно, ниже разобрано.

Если ты уже читал первую инструкцию (`ПОШАГОВАЯ-ИНСТРУКЦИЯ.md`, вариант с
цепочкой Cloudflare → Fly.io → Google) — этот документ намного короче,
потому что нам не нужно поднимать никаких своих серверов. Только Cloudflare.

Документ написан так, чтобы ты мог не знать ничего про сервера, WebSocket,
JavaScript и прочую техническую кухню. Просто открываешь, идёшь по шагам.

## В чём разница между двумя вариантами

Есть два способа собрать прокси для Liv. Оба работают, но они решают
разные задачи. Сравним:

| Параметр | Direct-mode (этот документ) | Chain-mode (первый документ) |
|---|---|---|
| Сколько сервисов | 1 (только Cloudflare) | 2 (Cloudflare + Fly.io) |
| Нужна банковская карта | **Нет** | Да (для Fly.io) |
| Время деплоя | ~10 минут | ~25–30 минут |
| Скорость / пинг | **Быстрее** на ~150–250мс на каждое сообщение | Медленнее (трафик идёт через США) |
| Надёжность | Зависит от того, в какую страну Cloudflare посадит твой воркер; Google может в любой момент решить блокировать | Надёжно, потому что Fly.io жёстко стоит в США / ЕС |
| Подходит, если | Хочется быстрее и проще, готов мириться, что иногда отвалится | Хочется чтобы работало стабильно даже когда Google закручивает гайки |

### Когда выбрать direct-mode (этот документ)

- Не хочется возиться с регистрацией на Fly.io и привязкой карты.
- Хочется минимальный пинг — direct-mode даёт ~100–150мс в обе стороны
  вместо ~300–400мс через цепочку.
- Готов раз в N недель открыть Cloudflare и поправить ошибку, если
  Google вдруг заблокирует исходящий узел.

### Когда выбрать chain-mode (первый документ)

- Если direct-mode сразу не работает (Google пишет «User location is not
  supported»). Это значит Cloudflare Smart Placement посадил твой воркер
  в страну, которую Google режет.
- Если хочется максимально надёжно и плевать на лишние ~200мс пинга.

### Совет: можно сделать оба

В Cloudflare на одном бесплатном аккаунте можно держать **до 30 воркеров**.
Можно сделать direct-mode основным, а chain-mode (или ещё один direct в
другом регионе) — резервным. Если основной отвалился, в Liv в настройках
меняешь адрес прокси на резервный и продолжаешь работать. Ниже в FAQ
показано, как это удобно организовать.

## Что понадобится

- Компьютер с интернетом (любой — Windows/Mac/Linux).
- Почта для регистрации на Cloudflare (можно ту же, что для Liv).
- Для регистрации на Cloudflare карта **не нужна**.
- Если ты в Беларуси/России — VPN на 5–10 минут только для шага
  регистрации/деплоя. После того, как воркер задеплоен, VPN не нужен.
- ~10 минут свободного времени.

**Чего НЕ нужно:**
- Никакой банковской карты.
- Никакой установки терминалов и `flyctl`.
- Никакого `git`, `Python` и пр. — всё делается через сайт Cloudflare.

## ЧАСТЬ 1. Cloudflare Worker

Cloudflare Worker — это маленький кусочек кода (на JavaScript), который
живёт на серверах Cloudflare и срабатывает, когда кто-то заходит на
твой адрес `https://что-нибудь.workers.dev`. Этот код мы напишем так,
чтобы он принимал WebSocket от Liv и пересылал его в Google.

Хорошее свойство домена `*.workers.dev`: его пропускают практически все
интернет-провайдеры в мире, **включая** РБ и РФ. Поэтому Liv сможет
достучаться до этого адреса напрямую, без VPN.

### Шаг 1.1. Регистрация на Cloudflare

1. Открой [https://dash.cloudflare.com/sign-up](https://dash.cloudflare.com/sign-up).
   - Если сайт не открывается — включи VPN на этом этапе. Только для
     регистрации.
2. Введи email и придумай пароль. Жми **Sign Up**.
3. Cloudflare пришлёт тебе письмо подтверждения. Открой его, нажми на
   ссылку «Verify email».
4. После верификации тебя перекинет в дашборд. Карта **не потребуется**.

### Шаг 1.2. Создаём Worker

1. В дашборде Cloudflare в левом меню найди раздел **Workers & Pages**.
   - Если меню свёрнуто, разверни его. Если не нашёл — иконка похожа на
     прямоугольник со скобками `</>`.
2. Нажми кнопку **Create application** (синяя справа сверху).
3. На следующем экране две вкладки: **Workers** и **Pages**. Нужна
   **Workers** (она часто открыта по умолчанию).
4. Найди вариант **Hello World** или **Start with Hello World!**. Жми
   на него. Появится поле для имени воркера.
5. Введи имя, например `livvv-proxy`. Имя должно быть уникальным внутри
   твоего аккаунта Cloudflare. После имени Cloudflare покажет тебе
   итоговый адрес: `https://livvv-proxy.<твой-subdomain>.workers.dev`.
   Запиши себе этот адрес — он пригодится в Liv.
6. Жми **Deploy**. Через несколько секунд воркер создан и работает (но
   пока внутри только заглушка «Hello World»).

### Шаг 1.3. Вставляем правильный код

1. После деплоя Cloudflare покажет страницу твоего воркера. Найди кнопку
   **`</>` Edit code** (или просто **Edit code**). Жми.
2. Откроется редактор. В левой панели файл называется `worker.js` (или
   `index.js`). В нём дефолтный код, который выводит «Hello World».
3. **Полностью удали** содержимое файла: щёлкни в редактор, нажми
   `Ctrl+A` (или `Cmd+A` на Mac) — выделит всё; потом `Delete` или
   `Backspace`. Файл должен стать пустым.
4. **Скопируй полностью** код из секции ниже (от первой до последней
   строки) и **вставь** в редактор. Это весь код целиком — его не надо
   дополнять, дописывать или склеивать. Просто скопировал-вставил.

```javascript
// Cloudflare Worker — Liv proxy "Direct mode" v2.
// Единственный файл, который пересылает WebSocket от Liv напрямую
// в Google Generative Language API. Никаких других серверов не нужно.
//
// Декодирование бинарных кадров в текст — обязательная часть, иначе в
// Firefox JSON.parse падает с ошибкой "unexpected character at line 1
// column 2 of the JSON data". Подробнее в FAQ к инструкции.

const UPSTREAM_HOST = 'generativelanguage.googleapis.com';

export default {
  async fetch(request) {
    const url = new URL(request.url);
    const upgradeHeader = request.headers.get('Upgrade');

    if (upgradeHeader !== 'websocket') {
      if (url.pathname === '/debug') return debug(request);
      if (url.pathname === '/' || url.pathname === '/health') {
        return new Response(
          'Liv proxy is alive (direct mode v2). Use WebSocket to /ws/...\n',
          {
            headers: {
              'Content-Type': 'text/plain; charset=utf-8',
              'Access-Control-Allow-Origin': '*',
            },
          },
        );
      }
      return new Response('Expected WebSocket upgrade', { status: 426 });
    }

    // CF Workers fetch() с Upgrade: websocket требует схему https://, не wss://.
    const upstreamUrl = `https://${UPSTREAM_HOST}${url.pathname}${url.search}`;

    let upstream;
    try {
      const upstreamResp = await fetch(upstreamUrl, {
        headers: { Upgrade: 'websocket' },
      });
      upstream = upstreamResp.webSocket;
      if (!upstream) {
        return new Response(
          'Failed to upgrade upstream connection (status ' + upstreamResp.status + ')',
          { status: 502 },
        );
      }
    } catch (err) {
      return new Response('Upstream connect failed: ' + (err && err.message), { status: 502 });
    }
    upstream.accept();

    const [client, server] = Object.values(new WebSocketPair());
    server.accept();

    const closeBoth = (code, reason) => {
      try { server.close(code, reason); } catch (_) {}
      try { upstream.close(code, reason); } catch (_) {}
    };

    // Браузер -> Google: пересылаем сообщения как есть.
    server.addEventListener('message', (event) => {
      try {
        upstream.send(event.data);
      } catch (_) {
        closeBoth(1011, 'forward to upstream failed');
      }
    });

    // Google -> Браузер: Gemini Live шлёт JSON внутри бинарных WS-кадров.
    // Firefox криво декодирует Blob -> "JSON.parse: unexpected character".
    // Любые не-string данные пробуем декодировать как UTF-8 и пересылать
    // как текстовый кадр. Если декодировать не получилось (вдруг сырое
    // аудио в будущем) — пересылаем как есть.
    const decoder = new TextDecoder('utf-8', { fatal: false });
    upstream.addEventListener('message', async (event) => {
      try {
        let data = event.data;
        if (typeof data !== 'string') {
          try {
            if (typeof Blob !== 'undefined' && data instanceof Blob) {
              data = decoder.decode(await data.arrayBuffer());
            } else {
              data = decoder.decode(data);
            }
          } catch (_) {
            data = event.data;
          }
        }
        server.send(data);
      } catch (_) {
        closeBoth(1011, 'forward to client failed');
      }
    });

    server.addEventListener('close', (event) => closeBoth(event.code || 1000, event.reason || ''));
    upstream.addEventListener('close', (event) => closeBoth(event.code || 1000, event.reason || ''));
    server.addEventListener('error', () => closeBoth(1011, 'client error'));
    upstream.addEventListener('error', () => closeBoth(1011, 'upstream error'));

    return new Response(null, { status: 101, webSocket: client });
  },
};

async function debug(request) {
  const cf = request.cf || {};

  let egressTrace = 'unavailable';
  try {
    const traceResp = await fetch('https://www.cloudflare.com/cdn-cgi/trace');
    egressTrace = await traceResp.text();
  } catch (err) {
    egressTrace = 'fetch failed: ' + (err && err.message);
  }

  let upstreamHealth = 'unavailable';
  try {
    const r = await fetch('https://' + UPSTREAM_HOST + '/');
    upstreamHealth = r.status + ' (Google reachable)';
  } catch (err) {
    upstreamHealth = 'upstream fetch failed: ' + (err && err.message);
  }

  const body = [
    '== inbound (where YOU hit the worker) ==',
    'colo:    ' + (cf.colo || '?'),
    'country: ' + (cf.country || '?'),
    'region:  ' + (cf.region || '?'),
    '',
    '== outbound (where the worker calls upstream FROM) ==',
    egressTrace,
    '',
    '== upstream (' + UPSTREAM_HOST + ') ==',
    upstreamHealth,
  ].join('\n');

  return new Response(body, {
    headers: { 'Content-Type': 'text/plain; charset=utf-8' },
  });
}
```

5. **Что в этом коде менять?** — **Ничего.** В отличие от chain-mode,
   тут `UPSTREAM_HOST` уже выставлен правильно
   (`generativelanguage.googleapis.com`) — это адрес самого Google.
   Просто скопировал, вставил, ничего не правишь.

6. Жми кнопку **Deploy** (или **Save and deploy**) сверху справа.
   Появится зелёный значок «Deployed».

### Шаг 1.4. Включаем Smart Placement (важно!)

Без этого шага Cloudflare запустит твой воркер в дата-центре, который
ближе всего к **тебе** (например, в Варшаве). А нам нужно, чтобы он
запускался ближе к **Google** (в США или ЕС). Это и делает Smart
Placement.

1. В редакторе кода, или вернувшись на страницу воркера, найди вкладку
   **Settings** (вверху или в боковой панели).
2. Найди раздел **Placement** (если он не виден сразу — пролистай или
   разверни «General settings»).
3. У тебя там будет переключатель `Off / Smart`. Поставь **Smart**.
4. Нажми **Save**.

Cloudflare после этого начнёт собирать статистику (минут 5–15) и
постепенно переедет твой воркер в дата-центр поближе к Google. Вначале
может сидеть в твоём ближайшем (Варшава, Москва), потом подвинется в
Лондон, Амстердам или США.

### Шаг 1.5. Проверяем, что воркер работает

1. Сними VPN (если он был включён).
2. Открой в браузере:
   ```
   https://<твой-адрес-воркера>.workers.dev/health
   ```
   (вместо `<твой-адрес-воркера>` подставь то, что Cloudflare показал
   тебе при создании, например `livvv-proxy.artemhttp.workers.dev`).

   Должен показаться текст:
   ```
   Liv proxy is alive (direct mode v2). Use WebSocket to /ws/...
   ```
   Если показывается — отлично, воркер запущен и доступен из РБ/РФ.

3. Открой страницу `/debug`:
   ```
   https://<твой-адрес-воркера>.workers.dev/debug
   ```
   Тут много буковок. Тебе нужны две секции:

   **`== inbound ==`** — это про тебя. Должны быть значения вроде
   `colo: WAW`, `country: BY`. Это нормально — сюда попадаешь ты сам.

   **`== outbound ==`** — это самое важное. Внутри этой секции есть
   строка `loc=XX`. **Это страна, из которой твой воркер ходит в Google.**

   Возможные значения:

   | `loc=` | Что это значит | Заработает? |
   |---|---|---|
   | `US` | США | ✅ Да |
   | `DE`, `NL`, `GB`, `FR`, `IE` | Европа (Германия/Нидерланды/Британия/Франция/Ирландия) | ✅ Скорее всего да |
   | `PL` | Польша | ⚠️ Иногда работает, иногда нет (как раз это сейчас сработало в твоём случае) |
   | `RU`, `BY` | Россия / Беларусь | ❌ Точно не сработает |
   | `IR`, `CU` | Иран / Куба | ❌ Точно не сработает |

   Если у тебя `loc=US` или `loc=DE` — Liv заработает.
   Если `loc=PL` — попробуй, но возможно надо будет переключиться на
   chain-mode (см. часть 3).
   Если `loc=BY` или `loc=RU` — Smart Placement не сработал, переключайся
   на chain-mode.

   **`== upstream (generativelanguage.googleapis.com) ==`** — это
   проверка, что Google в принципе отвечает. Если показано `404 (Google
   reachable)` — отлично, это нормально (Google не разрешает GET по
   корневому пути, но сам отвечает, значит сетевая связность есть).

## ЧАСТЬ 2. Подключение в Liv

Воркер готов и работает. Теперь скажем Liv, что он должен через него
ходить.

### Шаг 2.1. Открываем настройки Liv

1. Открой Liv (твоё приложение).
2. Зайди в **Настройки**.
3. Прокрути до раздела **«Маршрут (для стран с блокировкой)»**.

### Шаг 2.2. Включаем прокси и вставляем адрес

1. Включи переключатель **«Подключаться через прокси»**.
2. В поле **«Адрес прокси»** вставь адрес твоего воркера. Например:
   ```
   livvv-proxy.artemhttp.workers.dev
   ```
   - **Без** `https://` спереди (но если случайно вставишь с `https://`,
     Liv сам уберёт префикс).
   - **Без** `/` в конце.
   - Можно вставить и полный URL — лишнее обрежется.

### Шаг 2.3. Запускаем сессию

1. Закрой настройки, вернись в основной экран Liv.
2. Запусти разговор.
3. В журнале событий должна появиться строка вроде:
   ```
   Соединение через прокси: wss://livvv-proxy.artemhttp.workers.dev/...
   Подключение к Gemini Live установлено
   ```
4. Скажи что-нибудь — Liv должен ответить голосом, как обычно.

Если работает — поздравляю, прокси готов. 🎉

Если **не** работает — переходи к части 3.

## ЧАСТЬ 3. Если Google не пропускает (резервный план)

В Liv появилась ошибка вроде:
- `User location is not supported for the API use`
- `The user location is not supported`
- Или просто отвал «Connection closed» в первые секунды.

Это значит, что Cloudflare Smart Placement посадил твой воркер в страну,
которую Google режет (Польша часто, Россия/Беларусь почти всегда).
Direct-mode не сработает с такого узла. Что делать:

### Вариант А — подождать и переразвернуть

Smart Placement иногда «учится» и через день-два сам переезжает в более
удачный дата-центр. Можно просто подождать 24 часа и снова открыть
`/debug` — `loc=` могло смениться.

Если уж совсем хочется ускорить — можно зайти в Cloudflare → Worker →
Settings и нажать **Redeploy** (это обычно меняет место, куда CF
посадил воркер).

### Вариант Б — переключиться на chain-mode

Это вариант с цепочкой Cloudflare → Fly.io → Google. Подробнее в файле
`ПОШАГОВАЯ-ИНСТРУКЦИЯ.md` (первая инструкция). Главное отличие — там
нужно поднять Fly.io-приложение в США/ЕС, к которому будет ходить
Cloudflare. Это +20 минут работы и привязка карты для Fly.io, но
работает 100%.

Можно держать **оба воркера одновременно**:
- `livvv-proxy.workers.dev` — direct-mode (быстрый, иногда отваливается)
- `livvv-proxy-2.workers.dev` — chain-mode (медленнее, но стабильно)

Когда основной отваливается, в Liv заходишь в настройки и меняешь
адрес на резервный.

## FAQ — ответы на частые вопросы

### Q1. Почему вообще нужен какой-то прокси? Liv же работает у других без него.

Google Gemini API проверяет, из какой страны к нему пришёл запрос. Из
США/ЕС/Японии — пропускает. Из РФ, РБ, Ирана, Кубы и нескольких других
стран — отказывает с ошибкой «User location is not supported». Если
твой провайдер — белорусский или российский, Google видит твой IP и
говорит «нет». VPN решает это, но у VPN свои минусы (нужно везде
включать, тормозит остальной интернет, иногда платный). Прокси —
альтернатива: трафик к Google идёт через Cloudflare (страна, где Google
пропускает), всё остальное (соцсети, видео и т.д.) идёт у тебя как
обычно.

### Q2. В чём разница между direct-mode и chain-mode? Я уже не помню.

| | Direct-mode | Chain-mode |
|---|---|---|
| Сколько сервисов | 1 (Cloudflare) | 2 (Cloudflare + Fly.io) |
| Карта нужна? | Нет | Да (для Fly.io) |
| Пинг | Быстрее (~100–150мс RTT) | Медленнее (~300–400мс RTT) |
| Надёжность | Зависит от везения с Smart Placement | Высокая |
| Кому подходит | Хочется быстро и просто, готов мириться с редкими отвалами | Хочется максимально стабильно |

### Q3. Что такое Smart Placement и зачем оно нужно?

Cloudflare имеет ~300+ дата-центров по всему миру. По умолчанию воркер
запускается в том дата-центре, который ближе всего к **тому, кто его
вызывает** (то есть к тебе, в Варшаве или Москве). Это быстро для
самого воркера, но плохо для нас — Google режет такие IP.

Smart Placement переворачивает логику: вместо «ближе к пользователю»
Cloudflare начинает запускать воркер «ближе к серверу, к которому он
сам обращается». В нашем случае воркер обращается к Google в США, поэтому
Smart Placement постепенно переезжает воркер в США/ЕС.

Это **бесплатная** функция, и она строго лучше для нашей задачи.
Включай всегда.

### Q4. Что значит ошибка «JSON.parse: unexpected character at line 1 column 2 of the JSON data»?

Это была первая большая проблема, которую мы решали. Краткая суть:

Google Gemini Live посылает свои JSON-сообщения **внутри бинарных
WebSocket-кадров** (это формально странно, обычно JSON шлют в текстовых
кадрах, но у Google так). Когда такой бинарный кадр приходит браузеру
напрямую, Firefox пытается его распаковать через `Blob.text()` — и
иногда теряет первые байты. Получается строка вроде `{"r..."` без
открывающей скобки или с лишним символом, и `JSON.parse` падает с этой
ошибкой.

Решение — переупаковать бинарный кадр в текстовый прямо на стороне
Cloudflare Worker. Это и делает блок кода в скрипте:

```javascript
const decoder = new TextDecoder('utf-8', { fatal: false });
upstream.addEventListener('message', async (event) => {
  ...
  if (typeof data !== 'string') {
    try {
      if (typeof Blob !== 'undefined' && data instanceof Blob) {
        data = decoder.decode(await data.arrayBuffer());
      } else {
        data = decoder.decode(data);
      }
    } catch (_) {
      data = event.data;
    }
  }
  server.send(data);
  ...
});
```

Не трогай этот блок. Если случайно его удалишь — вернётся ошибка.

### Q5. Что значит ошибка «User location is not supported for the API use»?

Это значит, что Google посмотрел на исходящий IP воркера и решил, что
он из «неразрешённой» страны. Чаще всего так бывает, когда Smart
Placement временно посадил воркер в Польшу/Москву. Решения:

1. Подожди 1–2 дня — Smart Placement может переехать.
2. Зайди в Cloudflare → Worker → Settings → Redeploy. Иногда после
   этого CF выбирает другой дата-центр.
3. Переключись на chain-mode (cм. часть 3).

### Q6. Что значит ошибка «Fetch API cannot load: wss://...»?

Это значит, что в коде воркера в строке формирования upstreamUrl стоит
`wss://`, а должно быть `https://`. Проверь, что у тебя в коде:

```javascript
const upstreamUrl = `https://${UPSTREAM_HOST}${url.pathname}${url.search}`;
```

Именно `https://`, а не `wss://`. Это особенность Cloudflare Workers —
для исходящего WebSocket-соединения через `fetch()` они требуют
HTTPS-схемы и заголовка `Upgrade: websocket`.

### Q7. Можно ли иметь два воркера сразу — основной и резервный?

Да, это даже рекомендуется. На бесплатном Cloudflare можно создать до
30 воркеров.

Делаешь так:

1. По шагам 1.1–1.5 этой инструкции создаёшь первый воркер
   `livvv-proxy.workers.dev` — direct-mode.
2. Создаёшь второй воркер с другим именем (например `livvv-proxy-2`).
   В нём вставляешь либо тот же direct-код, либо chain-mode код из
   первой инструкции.
3. В заметках на телефоне записываешь оба адреса:
   - Быстрый: `livvv-proxy.artemhttp.workers.dev`
   - Резервный: `livvv-proxy-2.artemhttp.workers.dev`

Когда основной отваливается, в Liv в настройках меняешь адрес на
резервный. Всё.

### Q8. Что значит `loc=` в /debug?

Это страна, из которой исходит запрос воркера к Google. Cloudflare
определяет её по IP того дата-центра, в котором сейчас запущен твой
воркер.

- `loc=US` — США (Google пропустит)
- `loc=DE`, `NL`, `GB`, `FR`, `IE` — ЕС (скорее всего пропустит)
- `loc=PL` — Польша (как повезёт; в этой инструкции у нас сработало)
- `loc=RU`, `BY` — точно не пропустит
- `loc=IR`, `CU` — точно не пропустит

Если у тебя `loc=` плохой — Smart Placement ещё не переехал в США.
Подожди или переключайся на chain-mode.

### Q9. Если Google однажды забанит мой `loc=PL` IP — что делать?

Несколько вариантов в порядке возрастания трудозатрат:

1. **Сразу:** в Liv поменяй адрес прокси на резервный воркер
   (chain-mode). Liv продолжит работать, ты не теряешь сессию.
2. **Позже:** зайди в Cloudflare → Worker → Settings → Redeploy.
   Иногда после этого CF выбирает другой дата-центр, и воркер снова
   сидит в нормальной стране.
3. **Если ничего не помогает:** значит, Cloudflare у тебя всегда сидит
   в Польше (так бывает с Smart Placement). Переключись на chain-mode
   как основной. Direct-mode можно держать на потом, если ситуация
   изменится.

### Q10. Сколько у меня запросов в день?

Три разных лимита, у каждого свой:

- **Cloudflare Workers (этот воркер):** 100 000 запросов/день. Одна
  сессия Liv = 1 запрос. Никогда не упрёшься.
- **Google Gemini API:** 250 запросов/день на бесплатном тарифе. Одна
  сессия Liv = 1 запрос. Если 20 разговоров в день — потолка не
  достичь.
- **(Если используешь chain-mode) Fly.io:** 3 виртуалки × 256MB. Хватает
  на одного-двух пользователей.

Если упрёшься в лимит Google — включи платный тариф (там $300
бесплатных кредитов, потом ~$0.07 за минуту разговора), либо чередуй
несколько API-ключей на разных аккаунтах.

### Q11. Что такое `cf.country`, `cf.colo` и `cf.region` в /debug?

Это **где сидит ТЫ**, не воркер. То есть как Cloudflare видит твой
браузер. Полезно, чтобы понять, что воркер до тебя доходит.

- `colo` — код дата-центра CF, в который ты попал (например, `WAW` =
  Варшава).
- `country` — твоя страна по IP (например, `BY`).
- `region` — твой регион (например, `Minsk City`).

Эти строки никак не влияют на работу прокси — это просто
диагностическая информация.

### Q12. Воркер «засыпает» как Fly.io?

**Нет.** Cloudflare Workers всегда «горячие» — нет холодных стартов и
засыпания. Первое подключение всегда быстрое. В этом одно из
преимуществ direct-mode перед chain-mode.

### Q13. Можно ли я вписан в адрес прокси какой-то «левый» прокси из интернета (типа `http://1.2.3.4:8080`)?

Нет. В Liv поле «Адрес прокси» ожидает **специально написанный
WebSocket-прокси**, который понимает протокол Gemini Live (открывает
соединения к `generativelanguage.googleapis.com/ws/...`). Обычные
HTTP/SOCKS-прокси из интернета это не умеют. Только наш Cloudflare
Worker (или его аналог).

### Q14. Что делать, если /health открывается, но Liv всё равно «Connection closed»?

Открой `/debug` и посмотри:
- Если `loc=` плохой — это локационный бан, см. Q5.
- Если `upstream (...)` показывает что-то кроме `404 (Google reachable)`
  — проблема с сетевой связностью между CF и Google. Зайди в
  Cloudflare → Worker → Logs (если есть) и посмотри что в ошибках.
- Если всё выглядит нормально — посмотри в Liv в журнале событий
  точную ошибку и пришли её мне.

### Q15. Безопасно ли это? Кто-то может украсть мой API-ключ?

Адрес твоего воркера — публичный. Если кто-то узнает его, он сможет
ходить через него к Google **со своим собственным API-ключом**. Это не
утечка твоего ключа: твой API-ключ хранится только у тебя в браузере
Liv, через прокси он передаётся «насквозь» (Cloudflare и Google видят
его в URL-параметре `?key=`, но не сохраняют). Третье лицо, узнавшее
твой адрес воркера, не получит доступа к твоим разговорам или ключу —
только сможет «раздавать» себя своим знакомым через твой бесплатный
тарифа CF.

Если хочешь это закрыть — можно добавить в воркер проверку секретного
заголовка или origin (например `https://liv.tw...`). Для личного
использования и небольшой компании друзей — это нестрашно.

### Q16. Какие ещё есть полезные вещи в дашборде Cloudflare?

- **Workers & Pages → твой воркер → Logs** — можно включить «Begin log
  stream» и в реальном времени видеть запросы к воркеру. Полезно для
  отладки.
- **Workers & Pages → твой воркер → Settings → Triggers → Custom
  Domains** — если у тебя есть свой домен, можешь привязать его к
  воркеру (например `proxy.твой-домен.ru`). Тогда не нужен
  `*.workers.dev` адрес.
- **Account → Workers Free → Daily Requests** — счётчик использования.
  100 000 в день, обновляется в полночь UTC.
